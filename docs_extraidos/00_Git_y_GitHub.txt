Guía de Git y GitHub — control de versiones para Programación IV
Parte 1 — ¿Qué problema resuelve Git? (conceptos)
1.1 El problema sin control de versiones
Antes de usar Git, la forma "natural" de cuidar un proyecto es duplicar carpetas: taskflow, taskflow_final, taskflow_final_v2, taskflow_final_v2_arreglado. Esto falla rápido:
No queda claro qué cambió entre una copia y otra.
Si dos personas tocan el mismo proyecto, no hay forma ordenada de combinar sus cambios.
Si algo se rompe, hay que buscar "a mano" en qué copia estaba la última versión que funcionaba.
Git es un programa (un sistema de control de versiones) que resuelve esto llevando un historial exacto de cada cambio hecho a cada archivo, con fecha, autor y un mensaje que explica el porqué. En vez de duplicar carpetas, hay una sola carpeta y Git guarda "por dentro" todas las versiones anteriores.
💡 Nota del docente
Git corre 100% en la computadora de cada uno: no necesita internet para funcionar. Es un programa que ustedes ya tienen instalado (lo verificamos en el Paso 1) y que opera sobre los archivos de su disco.
1.2 ¿Dónde se guardan realmente los archivos?
Este es un punto que genera confusión y merece explicarse con precisión.
Cuando ejecutan git init dentro de una carpeta (por ejemplo taskflow/), Git crea ahí mismo una subcarpeta oculta llamada `.git` (taskflow/.git/). Ahí, y solo ahí, es donde Git guarda todo su historial: cada versión de cada archivo que ustedes hayan confirmado (hicieron commit), quién lo hizo y cuándo.
La carpeta taskflow/.git/ es una base de datos propia de Git, comprimida y con un formato interno (objetos, referencias, etc.). No es necesario entenderla en detalle, pero sí saber que existe y vive dentro del proyecto.
Si borran la carpeta .git, pierden todo el historial (aunque los archivos actuales sigan estando, tal como están en este momento). Por eso nunca se borra a mano.
Los archivos "de trabajo" que ven y editan en VS Code (manage.py, core/models.py, etc.) son la versión actual — lo que Git llama el working directory (directorio de trabajo). Las versiones anteriores no están "sueltas" en ningún lado visible: están empaquetadas dentro de .git/.
💡 Nota del docente
Se puede confirmar que existe con un comando simple. En Linux/Mac: ls -la (el flag -a muestra archivos ocultos, que empiezan con un punto). En Windows (PowerShell): dir -Force. Van a ver .git listada como una carpeta más.
1.3 Los tres estados de un archivo en Git
Todo archivo dentro de un repositorio Git está, en cada momento, en uno de estos tres estados:
Modificado (working directory): lo editaron, pero Git todavía no lo está "vigilando" para el próximo commit.
Preparado / en el área de stage (`staging area` o `index`): le dijeron a Git "este cambio quiero que forme parte del próximo commit" (con git add).
Confirmado (committed): ya quedó guardado permanentemente en el historial de .git/ (con git commit).
Analogía: imaginen que están armando una mudanza. Los archivos modificados son los objetos sueltos por la casa. git add es meterlos en una caja concreta que van a despachar (el staging area). git commit es cerrar esa caja, etiquetarla con una descripción y guardarla definitivamente en el depósito (el historial).
1.4 ¿Qué es GitHub, y en qué se diferencia de Git?
Git es el programa que corre en la computadora de cada uno. GitHub es un servicio web (una empresa, propiedad de Microsoft) que aloja copias de repositorios Git en internet, y agrega funcionalidades sociales/colaborativas por encima: interfaz visual, control de permisos, Pull Requests, Issues, y (lo que usamos en la Unidad 5) GitHub Actions para CI/CD.
El repositorio que tienen en su computadora (con su carpeta .git/) se llama repositorio local.
La copia que suben a github.com se llama repositorio remoto.
Git y GitHub son independientes: podrían usar Git toda la materia sin tocar GitHub jamás (guardando el historial solo en su máquina). Usamos GitHub porque agrega una copia de respaldo en internet y porque en la Unidad 5 vamos a usar GitHub Actions para el pipeline de CI/CD.
💡 Nota del docente
Existen alternativas a GitHub con el mismo rol de "alojar repositorios Git en la nube": GitLab y Bitbucket son las más conocidas. Todo lo que expliquemos sobre git push/git pull funciona igual con cualquiera de ellas — GitHub es simplemente la que vamos a usar en esta materia.
Parte 2 — Instalación y configuración inicial
2.1 Verificar si Git está instalado
Abran una terminal (en VS Code: menú Terminal > New Terminal) y ejecuten:
git --version
Si responde algo como git version 2.43.0, ya está instalado. Si da error de "comando no encontrado":
Windows: descarguen el instalador desde git-scm.com y sigan el asistente (opciones por defecto).
Mac: ejecuten xcode-select --install (instala herramientas de línea de comandos de Apple, que incluyen Git), o brew install git si tienen Homebrew.
Linux (Debian/Ubuntu): sudo apt update && sudo apt install git.
2.2 Configurar identidad
Git firma cada commit con un nombre y un correo. Esto se configura una sola vez por computadora (no por proyecto):
git config --global user.name "Nombre Apellido"
git config --global user.email "su_email@ejemplo.com"
--global significa que esta configuración aplica a todos los repositorios que usen desde esta computadora, no solo a taskflow. Pueden verificar lo configurado con:
git config --list
2.3 Crear una cuenta en GitHub
Si todavía no tienen una, regístrense en github.com con el mismo correo que configuraron en el paso anterior (no es obligatorio que coincida, pero simplifica el seguimiento de quién hizo cada commit).
Parte 3 — El flujo de trabajo básico: init, add, commit
3.1 Iniciar un repositorio
Ubicados dentro de la carpeta del proyecto (por ejemplo, taskflow/, la misma que crearon en la Clase 1):
cd taskflow
git init
Esto crea la carpeta oculta taskflow/.git/ mencionada en la Parte 1. A partir de este momento, Git "vigila" esta carpeta y todo lo que está dentro.
💡 Nota del docente
git init se ejecuta una sola vez por proyecto, al principio. No hay que repetirlo en cada clase.
3.2 Ver el estado del repositorio
El comando que van a usar constantemente, literalmente en cada sesión de trabajo:
git status
Les muestra tres cosas: en qué rama están, qué archivos están modificados pero no agregados (Changes not staged for commit), y qué archivos son nuevos y Git todavía no conoce (Untracked files).
3.3 El archivo `.gitignore`
No todo lo que hay en la carpeta del proyecto debe ir al historial de Git. El entorno virtual (venv/), archivos de configuración con secretos (.env), archivos compilados (__pycache__/) y bases de datos locales (db.sqlite3) no se versionan: son distintos en cada computadora, pesan mucho, o contienen información sensible.
En la raíz del proyecto (taskflow/.gitignore, al mismo nivel que manage.py):
venv/
.env
__pycache__/
*.pyc
db.sqlite3
*.log
Cada línea es un patrón: venv/ ignora esa carpeta completa; *.pyc ignora cualquier archivo con esa extensión, en cualquier subcarpeta.
💡 Nota del docente
Si un archivo ya estaba siendo trackeado por Git antes de agregarlo al .gitignore, agregarlo ahí no alcanza para que deje de aparecer: hay que quitarlo explícitamente del seguimiento con git rm --cached nombre_del_archivo.
3.4 Agregar archivos al área de stage
git add nombre_del_archivo.py      # un archivo puntual
git add core/                       # una carpeta completa
git add .                           # todo lo modificado/nuevo en la carpeta actual y subcarpetas
💡 Nota del docente
git add . es el más usado en la práctica diaria, pero hay que ser conscientes de qué se está agregando: por eso siempre se corre git status antes, para revisar la lista.
3.5 Confirmar los cambios (commit)
git commit -m "Agrega modelo Task y su primera migración"
El -m (message) es obligatorio en la práctica: un commit sin mensaje claro es casi inútil para el historial. Buenas prácticas de mensaje:
Modo imperativo y en español consistente: "Agrega...", "Corrige...", "Refactoriza...".
Corto (una línea de menos de 72 caracteres) y específico: no "cambios" o "fix", sino qué cambió y por qué.
3.6 Ver el historial
git log                 # historial completo, con hash, autor, fecha y mensaje
git log --oneline        # versión resumida, un commit por línea
Cada commit tiene un identificador único (hash, ej. a3f9c1e) que permite referenciarlo puntualmente más adelante (por ejemplo, para volver a esa versión exacta).
Parte 4 — Trabajar con GitHub: remotos, push y pull
4.1 Crear el repositorio remoto
En github.com: botón New repository. Le ponen nombre (ej. taskflow), lo dejan vacío (sin README, sin .gitignore generado por GitHub, porque ya tenemos uno local) y lo crean. GitHub va a mostrar una URL como:
https://github.com/su-usuario/taskflow.git
4.2 Conectar el repositorio local con el remoto
git remote add origin https://github.com/su-usuario/taskflow.git
origin es simplemente el nombre (una convención, podría llamarse de otra forma) que le damos a ese repositorio remoto dentro de nuestro repositorio local. Pueden verificar la conexión con:
git remote -v
4.3 Subir el historial (push)
git branch -M main
git push -u origin main
git branch -M main renombra la rama actual a main (el nombre estándar hoy en día para la rama principal).
git push -u origin main sube todos los commits locales al remoto origin, en la rama main. El flag -u (upstream) asocia la rama local main con la rama remota main, para que de ahora en más alcance con escribir git push a secas.
💡 Nota del docente
Recién en este momento los archivos existen "en la nube". Todo lo anterior (init, add, commit) fue exclusivamente local, en la carpeta .git/ de su computadora.
4.4 El ciclo diario de trabajo
De acá en adelante, el flujo que van a repetir en cada clase, después de cada avance concreto:
git status              # ver qué cambió
git add .                # preparar los cambios
git commit -m "Mensaje descriptivo del avance de hoy"
git push                 # subir a GitHub
💡 Nota del docente
Recuerden: git push sube commits que ya existen localmente. Si se olvidan de hacer git commit antes, no hay nada nuevo que subir. El orden siempre es: modificar código → add → commit → push.
4.5 Traer cambios (pull) — importante para trabajo en grupo o entre varias computadoras
Si trabajan el proyecto desde más de una computadora, o en equipo, antes de empezar a programar conviene traer lo último del remoto:
git pull
Si alguien más subió cambios a los mismos archivos que ustedes modificaron localmente sin haber hecho pull antes, puede aparecer un conflicto de merge: Git no sabe cuál de las dos versiones es la correcta y les pide que decidan a mano, editando el archivo (van a ver marcas como <<<<<<<, =======, >>>>>>> delimitando ambas versiones). Es un tema que profundizamos si surge en la práctica.
Parte 5 — Buenas prácticas para toda la materia
Commitear seguido y en unidades chicas: mejor varios commits pequeños y descriptivos ("Agrega serializer de Task", "Agrega validación de fecha límite") que uno enorme al final de la clase.
Nunca commitear secretos: repasen que .env esté en .gitignore antes del primer commit del proyecto.
Terminar cada clase con `git push`: es la garantía de que el trabajo queda respaldado en GitHub y no se pierde si algo le pasa a la computadora.
Leer siempre la salida de `git status` antes de un add/commit: evita subir archivos que no correspondían (por ejemplo, un archivo de datos de prueba pesado).
