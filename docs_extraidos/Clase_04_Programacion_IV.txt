Parte 1 — Routers, ViewSets y el CRUD automático (65 min)
1.1 De funciones a ViewSets
La clase pasada escribimos vistas función por función (project_list, task_list), y ambas eran de solo lectura. DRF nos da algo mucho más potente para cubrir el CRUD completo: ModelViewSet, una clase que ya sabe implementar list (GET a la lista), create (POST), retrieve (GET a un elemento puntual), update/partial_update (PUT/PATCH) y destroy (DELETE) para un modelo dado, con una fracción del código que nos hubiera llevado escribir cada una a mano.
Abran taskflow/core/views.py y reemplacen las funciones project_list y task_list (dejen health_check como está) por:
from rest_framework import viewsets
from .models import Project, Task
from .serializers import ProjectSerializer, TaskSerializer
 
 
class ProjectViewSet(viewsets.ModelViewSet):
    queryset = Project.objects.all()
    serializer_class = ProjectSerializer
 
 
class TaskViewSet(viewsets.ModelViewSet):
    queryset = Task.objects.select_related("project").prefetch_related("tags").all()
    serializer_class = TaskSerializer
Notar la diferencia estructural: antes teníamos una función por acción; ahora tenemos una clase por modelo, y esa clase resuelve las seis acciones del CRUD heredando de viewsets.ModelViewSet. queryset le dice al ViewSet de dónde sacar los datos base; serializer_class, qué serializer usar para convertirlos a JSON y validarlos.
1.2 Routers: generación automática de URLs
Hasta ahora armábamos cada path(...) a mano en core/urls.py. Un ModelViewSet necesita varias URLs relacionadas (lista y detalle, con distintos métodos HTTP cada una) — para no escribirlas todas a mano, usamos un Router.
Reemplacen todo el contenido de taskflow/core/urls.py:
from django.urls import path, include
from rest_framework.routers import DefaultRouter
from . import views
 
router = DefaultRouter()
router.register(r"projects", views.ProjectViewSet, basename="project")
router.register(r"tasks", views.TaskViewSet, basename="task")
 
urlpatterns = [
    path("health/", views.health_check, name="health_check"),
    path("", include(router.urls)),
]
DefaultRouter() crea el objeto encargado de generar las URLs; router.register(r"tasks", views.TaskViewSet, basename="task") le dice "registrá el ViewSet de tareas bajo el prefijo tasks/" — el prefijo r antes del string indica una raw string, convención habitual en patrones de URL de Django aunque acá no haya caracteres especiales. basename="task" es el nombre interno base para las URLs generadas (usado por Django para referenciarlas programáticamente). include(router.urls) inserta, dentro del mapa de URLs, todas las rutas que el router generó automáticamente.
Guarden y, con el servidor corriendo (python manage.py runserver desde taskflow/), visiten http://127.0.0.1:8000/api/tasks/. El DefaultRouter generó automáticamente:
GET /api/tasks/ → listar todas las tareas.
POST /api/tasks/ → crear una tarea nueva.
GET /api/tasks/<id>/ → ver el detalle de una tarea puntual.
PUT /api/tasks/<id>/ → reemplazar todos los campos de esa tarea.
PATCH /api/tasks/<id>/ → actualizar parcialmente esa tarea.
DELETE /api/tasks/<id>/ → eliminarla.
Prueben desde la Browsable API: al final de http://127.0.0.1:8000/api/tasks/ va a aparecer un formulario HTML generado automáticamente por DRF — usen ese formulario para crear una tarea nueva (eligiendo un project existente del desplegable), después entren a http://127.0.0.1:8000/api/tasks/1/ para verla, editar algún campo y guardarlo, y por último bórrenla con el botón DELETE que aparece en esa misma página.
Parte 2 — Códigos de estado HTTP (45 min)
2.1 ¿Por qué importan?
El código de estado le dice al cliente, sin que tenga que interpretar el cuerpo de la respuesta, qué pasó con su petición. ModelViewSet ya devuelve los correctos por defecto para cada acción, pero tienen que saber reconocerlos porque van a aparecer constantemente al depurar (y son estándar HTTP, no algo específico de Django):
200 OK: lectura exitosa (GET).
201 Created: creación exitosa (POST). El body incluye el recurso recién creado, con su nuevo id.
204 No Content: eliminación exitosa (DELETE). El body viene vacío a propósito.
400 Bad Request: los datos enviados no pasaron la validación (por ejemplo, falta un campo obligatorio).
401 Unauthorized / 403 Forbidden: no autenticado / autenticado pero no autorizado — los vemos en detalle en la Unidad 3.
404 Not Found: el recurso solicitado no existe (por ejemplo, /api/tasks/999/ si no hay tarea con id=999).
500 Internal Server Error: error no controlado del lado del servidor (un bug, no un dato inválido del cliente).
2.2 Verificación práctica con `curl`
curl es una herramienta de línea de comandos, gratuita y de código abierto, para hacer peticiones HTTP sin usar el navegador — muy útil para ver exactamente qué código de estado y qué headers devuelve el servidor. Viene preinstalada en Linux y Mac; en Windows 10/11 también viene incluida de fábrica en PowerShell y en el símbolo del sistema (si no la tienen, se instala junto con Git para Windows, que ya instalaron en la clase de Git). Ábranla en una terminal aparte (no hace falta el entorno virtual activo para usar curl, es un programa del sistema operativo, no de Python):
curl -i http://127.0.0.1:8000/api/tasks/999/
El flag -i (include) hace que curl muestre también los headers de la respuesta, incluyendo la primera línea con el código de estado. Observen el 404 en esa primera línea (asumiendo que no tienen una tarea con id=999).
Después, prueben un POST sin el campo obligatorio title:
curl -i -X POST http://127.0.0.1:8000/api/tasks/ \
  -H "Content-Type: application/json" \
  -d '{"project": 1}'
-X POST indica el método; -H "Content-Type: application/json" le avisa al servidor que el body viene en formato JSON; -d '...' es el body de la petición. Van a ver un 400 con el detalle de qué campo falló, generado automáticamente por la validación del serializer.
💡 Nota del docente
El carácter \ al final de línea sirve para partir un comando largo en varias líneas, y funciona tal cual en Linux, Mac y en Git Bash de Windows. Si están en PowerShell de Windows, reemplacen cada \ de fin de línea por una comilla invertida `  `; si están en el símbolo del sistema clásico (cmd.exe`), escriban todo el comando en una sola línea, sin saltos. Por simplicidad, en el resto de la materia recomendamos usar Git Bash (se instala junto con Git para Windows, Clase de Git y GitHub) como terminal en Windows, porque permite copiar los comandos exactamente como están escritos en esta guía.
Parte 3 — Validaciones de negocio y manejo centralizado de errores (75 min)
3.1 Validaciones a nivel de serializer
Las validaciones de "tipo de dato" (que title sea un texto, que due_date tenga formato de fecha válido) ya las hace DRF automáticamente, a partir de los tipos definidos en el modelo. Las reglas de negocio (condiciones propias de nuestra aplicación) las escribimos nosotros. Ejemplo: la fecha límite (due_date) no puede ser anterior a hoy.
Abran taskflow/core/serializers.py y modifiquen TaskSerializer:
from datetime import date
from rest_framework import serializers
from .models import Project, Task, Tag
 
 
class TaskSerializer(serializers.ModelSerializer):
    tags = TagSerializer(many=True, read_only=True)
 
    class Meta:
        model = Task
        fields = [
            "id", "project", "title", "description",
            "priority", "status", "due_date", "tags", "created_at",
        ]
 
    def validate_due_date(self, value):
        if value and value < date.today():
            raise serializers.ValidationError("La fecha límite no puede ser en el pasado.")
        return value
 
    def validate(self, data):
        # Validación que involucra más de un campo
        if data.get("status") == "completada" and not data.get("due_date"):
            raise serializers.ValidationError(
                "No se puede marcar una tarea como completada sin fecha límite registrada."
            )
        return data
Dos mecanismos distintos, complementarios: un método llamado exactamente validate_<nombre_del_campo> (acá, validate_due_date) valida ese único campo, recibe su valor ya "limpio" (convertido al tipo Python correcto) en el parámetro value, y debe devolverlo si es válido o levantar serializers.ValidationError(...) si no. El método validate(self, data) se ejecuta después, con todos los campos ya validados individualmente, disponibles en el diccionario data — sirve para reglas que cruzan varios campos (acá, status y due_date juntos). DRF llama a ambos automáticamente, en ese orden, antes de intentar guardar cualquier dato.
Prueben crear (POST) una tarea con due_date en el pasado y verifiquen el mensaje de error específico en la respuesta 400.
3.2 Manejo centralizado de excepciones
Por defecto, si ocurre un error de programación no capturado (una excepción de Python que nadie atrapó), DRF lo convierte en un 500 con un formato de respuesta no siempre consistente con el resto de nuestros errores. Vamos a interceptar todas las excepciones de la API en un solo lugar, para que el formato de error sea siempre el mismo, sea cual sea el problema.
Creen el archivo taskflow/core/exceptions.py:
from rest_framework.views import exception_handler
from rest_framework.response import Response
from rest_framework import status
 
 
def custom_exception_handler(exc, context):
    response = exception_handler(exc, context)
 
    if response is not None:
        response.data = {
            "error": True,
            "detail": response.data,
        }
        return response
 
    # Excepción no manejada por DRF (ej. un error de programación, un bug)
    return Response(
        {"error": True, "detail": "Error interno del servidor."},
        status=status.HTTP_500_INTERNAL_SERVER_ERROR,
    )
exception_handler es la función que trae DRF por defecto: la llamamos primero para que siga resolviendo los casos que ya sabe manejar (400, 404, 403, etc.), y envolvemos su resultado en nuestro propio formato ({"error": true, "detail": ...}). Si exception_handler no supo qué hacer con la excepción (response is None, típicamente un bug nuestro no relacionado con validación de datos), devolvemos manualmente un 500 con el mismo formato consistente.
Para activarlo, en taskflow/config/settings.py, agreguen (o creen si no existe todavía) el diccionario de configuración de DRF:
REST_FRAMEWORK = {
    "EXCEPTION_HANDLER": "core.exceptions.custom_exception_handler",
}
Prueben de nuevo el POST inválido de la Parte 2.2: ahora la respuesta viene envuelta con "error": true de forma consistente en toda la API, no solo en este endpoint puntual.

Diccionario de términos de esta clase
Código de estado HTTP: número de tres dígitos que indica el resultado de una petición HTTP (200, 404, 500, etc.).
`curl`: herramienta de línea de comandos, gratuita y preinstalada en Linux/Mac (e instalable en Windows), para hacer peticiones HTTP sin usar el navegador.
Excepción no manejada: un error de programación que nadie capturó con try/except, y que normalmente termina en un error 500.
Router: componente de DRF que genera automáticamente las URLs de un ViewSet.
Validación de negocio: una regla propia de la aplicación (no un simple chequeo de tipo de dato) que los datos deben cumplir para ser válidos.
ViewSet: clase de DRF que agrupa la lógica CRUD completa de un modelo en un solo lugar.
